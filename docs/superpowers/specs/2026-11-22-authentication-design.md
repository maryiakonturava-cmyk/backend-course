## 1. Цель

Продолжить существующий проект: добавить вход по email и паролю, опциональное email-подтверждение входа, выдачу пары JWT в cookies, обновление пары и выход. Спецификация должна позволять составить план без повторного восстановления требований из задания.

Регистрация по-прежнему не выдаёт JWT. Вход, refresh и каждая проверка access допускают только существующего пользователя со статусом `active`. Роли не берутся из JWT: будущий RBAC получает только проверенный `userId` и читает актуальные назначения на сервере.

### Входит в работу

- `POST /auth/login`.
- `POST /auth/login/confirm`: OTP и magic link.
- `POST /auth/login/resend` с сохранением метода попытки.
- `POST /auth/refresh` и `POST /auth/logout`.
- Общая проверка access-cookie для будущих защищённых операций.
- Отдельные login challenges, миграции, блокировки и ограничения уникальности.
- Валидация конфигурации при запуске, HTTPS, cookies, CORS и CSRF.
- Rate limiting, безопасный аудит, OpenAPI, health/readiness и тесты.
- Совместимость с существующей регистрацией и её тестами.

### Не входит в работу

- UI входа и страница обработки magic link. Их HTTP-контракт описывается, но frontend не создаётся.
- API настроек: флаг и метод подтверждения задаются конфигурацией.
- RBAC, CRUD пользователей, назначение ролей, сброс пароля, OAuth, MFA через приложения или SMS.
- Серверные refresh-сессии, хранение JWT, `jti`, denylist, обнаружение повторного refresh, выход со всех устройств.
- Перевод регистрации на magic link или изменение её ответов `201`/`202`/`409`.
- Переустройство решения в полную Clean Architecture.

### Что считается неприемлемым результатом

- JWT, пароль, его хеш, OTP, magic-link token или ключи попадают в ответ JSON либо журнал.
- Неизвестный email отличается от неверного пароля или неактивного статуса формой ошибки входа.
- Refresh принимается не из cookie или access подменяется refresh-токеном.
- Неактивный пользователь продолжает пользоваться криптографически действительным JWT.
- Одновременно подтверждаются две попытки одного пользователя либо один challenge используется повторно.
- Отказ БД превращается в `401`, SMTP вызывается до commit либо отправляется только одна cookie при ошибке подписи.
- Ради локального запуска снимается `Secure` или ослабляются production-проверки секретов.

## 2. Текущее состояние проекта

По состоянию на дату документа:

- Есть API-проект и Infrastructure-проект, общий `AppDbContext`, PostgreSQL, EF Core migrations, контроллер регистрации.
- `PasswordHasher.Verify` уже проверяет bcrypt; регистрация использует work factor 12 и ограничивает пароль 72 байтами.
- Есть `EmailNormalizer`, `OtpGenerator`, `SecretHasher`, SMTP через MailKit, локальный Mailpit.
- `UserStatus` содержит только `Pending` и `Active`; статусы сохраняются строками.
- `registration_challenges` относится только к регистрации. Причина погашения там отдельно не хранится.
- `IEmailSender.SendOtpAsync` и шаблон SMTP ориентированы на регистрацию; magic link не поддерживается.
- Нет JWT-аутентификации, access-проверки, CORS/CSRF для нового контракта и auth endpoints.
- В `Program.cs` есть IP rate limiter регистрации, HTTPS redirection и `GET /health`; проверка БД для readiness отсутствует.
- Docker публикует API по HTTP. Один redirect не создаёт рабочий HTTPS-вход в контейнер.
- Текущий `RegistrationAudit` пишет открытый email. Это необходимо исправить в затрагиваемом потоке логирования, а не копировать в authentication.
- Интеграционные тесты используют `WebApplicationFactory<Program>`, PostgreSQL Testcontainers и HTTPS base address.

README и прежний CLAUDE.md частично описывают исходный starter. При составлении плана фактический код и эта спецификация важнее устаревшего описания возможностей.

## 3. Рассмотренные подходы

### A. Отдельный auth-сервис или полная Clean Architecture

Изоляция сильнее, но появляются дополнительные проекты, сетевые границы или слои. Для продолжения существующего учебного проекта это лишняя сложность. Не выбирается.

### B. Общий универсальный механизм registration/login challenges

Уменьшает дублирование сущностей, но меняет уже работающую регистрацию. У неё другой контракт resend, поведение пятого неверного OTP и другой жизненный цикл пользователя. Объединение повышает риск регрессий и не требуется заданием. Не выбирается.

### C. Продолжение B-lite с отдельным модулем Authentication — предлагаемый вариант

Сохранить два проекта и общий `AppDbContext`. Добавить отдельные login challenges и auth-сервисы; переиспользовать существующие криптографические примитивы и SMTP-транспорт без переноса правил регистрации во вход.

Пользователь подтвердил, что это продолжение проекта и отдельный spec для будущего плана. Конкретное разбиение ниже — предложение для проекта, а не отдельное согласованное пользователем изменение архитектуры.

## 4. Границы компонентов

### API-проект

- Контроллер аутентификации, DTO и преобразование результатов в HTTP.
- Чтение/установка/удаление cookies с общей политикой атрибутов.
- Подключение общей access-проверки, rate limiting, CORS/CSRF и безопасного аудита.
- Регистрация зависимостей, startup validation, health/readiness, OpenAPI.

### Infrastructure-проект

- Модуль `Authentication/`: сценарии login/confirm/resend/refresh, login challenge, конфигурация, подпись и проверка JWT.
- Существующие `Users/`, общий `AppDbContext` и единое место миграций.
- Переиспользование `PasswordHasher.Verify`, нормализации email, OTP, HMAC и SMTP-транспорта.

Контроллеры остаются тонкими. Решения о статусах, секретах, транзакциях и порядке блокировок не переносятся в контроллеры. Отдельный repository/unit-of-work поверх `AppDbContext` не добавляется.

Отправку login OTP и magic link добавить минимальным расширением почтового контракта. Существующий вызов регистрации и смысл её письма сохранить; все реализации, включая тестовые отправители, обновить согласованно. Универсальный движок шаблонов не нужен.

## 5. Данные и инварианты

### 5.1. Пользователь

Существующая таблица пользователей остаётся общей. Нормализованный email сохраняет уникальный индекс. Добавить строковые статусы `Blocked`, `Deleting`, `Deleted` без изменения сохранённых значений `Pending`/`Active`.

Сериализация и сравнение доменных статусов должны соответствовать значениям задания: `pending`, `active`, `blocked`, `deleting`, `deleted`. Это не требует переименовывать существующие значения в БД, если текущий mapping обеспечивает нужную семантику. Неизвестный статус не должен разрешать доступ.

### 5.2. `login_challenges`

| Поле | Назначение |
| --- | --- |
| `id` | Случайный идентификатор попытки, используемый как `attemptId` |
| `user_id` | Ссылка на существующего пользователя |
| `method` | `otp` или `magic_link`; фиксируется при создании |
| `secret_hash` | HMAC-SHA256 секрета с отдельным login challenge key |
| `attempts` | Число неверных проверок OTP; изначально 0 |
| `last_sent_at` | Время последнего создания/замены секрета |
| `consumed_at` | Время погашения либо `NULL` |
| `consumed_reason` | `confirmed`, `replaced`, `attempts_exhausted`, `user_inactive` либо `NULL` |

**Решение для проекта:** TTL вычисляется из `last_sent_at + 600 секунд`; отдельный `expires_at` не хранится. Это не изменяет модель регистрационных challenges.

- Не более одной непогашенной login-попытки на `user_id`: частичный уникальный индекс по `user_id`, где `consumed_at IS NULL`.
- `consumed_at` и `consumed_reason` согласованы: либо оба отсутствуют, либо оба заданы.
- Счётчик OTP находится в диапазоне 0–5. Для magic link неверные секреты его не увеличивают.
- Успешное подтверждение или замена необратимо гасит старую попытку.
- Истечение TTL само по себе не гасит попытку: иначе нельзя выполнить разрешённый заданием resend просроченной попытки.
- Challenge принадлежит входу и никогда не активирует `pending` пользователя.
- Refresh JWT, полные JWT, исходные секреты и refresh-сессии в БД не сохраняются.

При физическом удалении пользователя существующий challenge нельзя считать подтверждаемым. План должен согласовать FK/удаление с обработкой исчезнувшего пользователя; не вводить новый пользовательский API удаления.

### 5.3. Конкурентность

Для login с подтверждением, confirm и resend порядок блокировок одинаков:

1. Определить `user_id`, если исходный запрос содержит только `attemptId`. Это чтение не разрешает вход.
2. В транзакции заблокировать строку пользователя.
3. Затем заблокировать строку попытки и перечитать её актуальное состояние.
4. После блокировок перепроверить статус, паузу и допустимость операции.

Использовать блокировки PostgreSQL и транзакции, а не только блокировки памяти процесса. Любые будущие операции, меняющие статус пользователя совместно с challenge, должны соблюдать тот же порядок.

Для прямого login, refresh и access статус проверяется в ходе каждого запроса. Блокировка пользователя после завершения проверки не отменяет уже выполняющийся запрос задним числом; следующий запрос обязан заново проверить статус. Для confirm изменение статуса сериализуется блокировкой пользователя.

## 6. Конфигурация и секреты

Обязательный внешний контракт конфигурации:

| Параметр | Правило |
| --- | --- |
| `LOGIN_EMAIL_CONFIRMATION_ENABLED` | Включает второй шаг для новых входов |
| `LOGIN_EMAIL_CONFIRMATION_METHOD` | Только `otp` или `magic_link` для новых попыток |
| `JWT_ACCESS_SECRET` | Отдельный случайный секрет, не менее 32 байт |
| `JWT_REFRESH_SECRET` | Другой случайный секрет, не менее 32 байт |
| `LOGIN_CHALLENGE_HMAC_KEY` | Отдельный случайный ключ, не менее 32 байт |
| `JWT_ISSUER` | Непустое значение, одинаковое при выпуске и проверке |
| `JWT_AUDIENCE` | Непустое значение, одинаковое при выпуске и проверке |
| SMTP | Существующие host/port/from и необходимые SMTP-настройки |
| Frontend origin и URL подтверждения | Доверенные адреса из конфигурации, не из запроса |

**Решения для проекта:**

- Новые криптографические секреты задаются как Base64 от случайных байтов; длина проверяется после декодирования. Пароль пользователя не декодируется и не нормализуется.
- Добавить `LOGIN_AUDIT_HMAC_KEY`: независимый случайный ключ минимум 32 байта для служебного идентификатора неизвестного email.
- Все перечисленные новые ключи различаются между собой; login challenge key также не переиспользует ключ регистрации.
- Внешние переменные с именами из задания явно привязать к типизированной конфигурации. Не предполагать автоматическое соответствие `JWT_ACCESS_SECRET` произвольному вложенному разделу.
- Отсутствующий, пустой, некорректно закодированный, короткий или повторно использованный обязательный ключ приводит к отказу запуска. Неверные issuer, audience, метод, origin или URL также не допускают запуск соответствующей конфигурации.
- JWT- и login challenge keys обязательны и при выключенном подтверждении. Переход между режимами не должен скрывать ошибочную конфигурацию.
- Не коммитить реальные ключи, не использовать встроенные тестовые значения для рабочего запуска и не генерировать ключи внутри запускающегося приложения.
- Для локального запуска ключи заранее предоставляет разработчик через environment или User Secrets. Тесты явно передают изолированную валидную конфигурацию и не ослабляют production validation.

Флаг и метод влияют только на новые попытки. Существующий challenge сохраняет метод и доступен для confirm/resend после смены метода или выключения второго шага. Изменение ключей не входит в динамические настройки этой работы.

## 7. HTTP-контракт

### 7.1. Общие правила

- JSON использует camelCase. Все auth POST принимаются только по HTTPS.
- Email: обязательная строка допустимого формата, trim и lowercase через существующее правило нормализации.
- Password: обязательная непустая строка; крайние и внутренние пробелы сохраняются. Не применять повторно регистрационное требование «буква + цифра» при входе.
- Сохранить защиту bcrypt от усечения: пароль длиннее 72 байт UTF-8 отклоняется валидацией до вызова bcrypt. Валидный ранее зарегистрированный пароль не должен изменяться при входе.
- Невалидная форма запроса даёт `400`, а не вычислительно дорогую проверку пароля.
- Ошибка входа: `401` с кодом `invalid_credentials`; ошибка сессии: `401` с `invalid_session`. Ответ не уточняет причину.
- Для новых ошибок использовать единый формат, совместимый с текущими API-ошибками. Обязательное поле `code` сохраняет коды задания; описание не содержит внутренних исключений или пользовательских данных.
- Для временной паузы отправки `429` содержит `retryAfterSeconds` и `Retry-After` с оставшимися целыми секундами, округлёнными вверх. На границе 60 секунд отправка разрешена.
- Ни один ответ не содержит пароль, хеш, JWT, OTP, magic-link token, HMAC, ключи, роли или признак существования аккаунта за пределами разрешённого успешного сценария.

### 7.2. `POST /auth/login`

Запрос:

```json
{
  "email": "user@example.com",
  "password": "unchanged password"
}
```

Порядок обработки:

1. Проверить Origin/CSRF, форму запроса и оба применимых rate limit до bcrypt.
2. Найти пользователя по нормализованному email.
3. Если пользователя нет, выполнить проверку с заранее подготовленным фиктивным bcrypt-хешем того же work factor. Не вычислять новый фиктивный хеш на каждый запрос.
4. Проверить пароль. Для неизвестного email, неправильного пароля и любого неактивного статуса вернуть одинаковый `401 invalid_credentials`. Не раскрывать статус и не пропускать проверку пароля только потому, что пользователь неактивен.
5. Если второй шаг выключен, создать оба JWT и лишь затем подготовить ответ с обеими cookies.
6. Если второй шаг включён, проверить время последней непогашенной попытки. До истечения 60 секунд вернуть `429`, не создавать попытку и не вызывать SMTP.
7. После паузы в одной транзакции заблокировать пользователя, затем прежнюю попытку; перепроверить `active` и паузу. Старую попытку погасить как `replaced`, создать новую с методом из текущей конфигурации и зафиксировать транзакцию.
8. Только после commit отправить письмо. Секрет доступен только построению почтового сообщения, не HTTP-ответу.

Ответы:

| Состояние | Ответ |
| --- | --- |
| Прямой вход успешен | `204`, две `Set-Cookie`, без тела |
| Второй шаг начат | `202`, тело ниже; JWT/cookies не выдаются |
| Реквизиты неверны или пользователь неактивен | `401 invalid_credentials` |
| Невалидный запрос | `400` |
| Rate limit или пауза отправки | `429` |
| БД, commit, SMTP или подпись недоступны | `503`, правила частичного состояния ниже |

```json
{
  "confirmationRequired": true,
  "method": "otp",
  "attemptId": "<идентификатор попытки>",
  "expiresInSeconds": 600,
  "resendAfterSeconds": 60
}
```

Для magic link значение `method` равно `magic_link`.

Если commit не состоялся, письмо не отправляется. Если SMTP отказал после commit, попытка сохраняется; вернуть `503` с `confirmationRequired: true`, `method`, `attemptId`, `retryAfterSeconds`. Время повтора вычисляется от сохранённого `last_sent_at`, а не начинается заново при формировании ответа. Новый login и resend используют одну и ту же паузу.

Если нельзя создать хотя бы один JWT прямого входа, вернуть `503` без любых `Set-Cookie`. При потере успешного ответа прямой вход можно повторить: серверной сессии нет.

### 7.3. `POST /auth/login/confirm`

Разрешена ровно одна из форм:

```json
{
  "attemptId": "<идентификатор попытки>",
  "code": "012345"
}
```

```json
{
  "token": "<attemptId>.<secret>"
}
```

- OTP — строка ровно из шести ASCII-цифр; ведущие нули значимы.
- Magic-link secret — 32 криптографически случайных байта до base64url-кодирования.
- Смешанные, неполные и не соответствующие методу сохранённой попытки формы дают `400` без проверки секрета и расхода OTP-счётчика.

Порядок:

1. Определить пользователя по попытке, затем заблокировать пользователя и challenge в установленном порядке. Отсутствующая попытка даёт `400`.
2. Для погашенного `attempts_exhausted` с пятью неверными вводами вернуть `429`. Для `confirmed`, `replaced`, `user_inactive` вернуть общий `400`.
3. При `now >= last_sent_at + 600 секунд` вернуть общий `400`, не увеличивая счётчик.
4. Если после блокировки пользователь отсутствует или не `active`, погасить ещё действующую попытку с `user_inactive`, зафиксировать изменение и вернуть `401 invalid_credentials`. Последующие обращения к ней дают `400`.
5. Вычислить HMAC-SHA256 присланного секрета и сравнить с сохранённым значением за постоянное время.
6. Неверный OTP увеличивает `attempts` в той же транзакции. Пятый ввод проверяется: правильный ещё может завершить вход. Пятый неверный даёт `400` и гасит попытку с `attempts_exhausted`; следующий запрос даёт `429`.
7. Неверный magic link даёт `400`; OTP-счётчик не применяется.
8. При верном секрете подписать оба JWT, погасить challenge с `confirmed`, выполнить commit и только затем установить обе cookies.

Успех — `204`, две cookies, без тела. Ошибка подписи или commit — `503`, без `Set-Cookie`; транзакция откатывается, подтверждение можно повторить. Если успешный ответ потерян после commit, challenge уже использован: требуется новый login.

### 7.4. Magic-link frontend-контракт

- Письмо содержит доверенный frontend URL с токеном только во фрагменте, например `https://frontend.example/login/confirm#token=<attemptId>.<secret>`.
- GET страницы или предпросмотр письма не подтверждает вход и не гасит challenge.
- Frontend извлекает token, удаляет его из видимого URL/history и выполняет отдельный POST `/auth/login/confirm`.
- При другом origin frontend отправляет credentials и `X-CSRF-Protection: 1`.
- Нельзя собирать адрес назначения из недоверенного `Host`, `Origin` или пользовательского redirect URL.
- Frontend не сохраняет token в долговременном хранилище, аналитике или журналах. Создание самой страницы вне scope.

### 7.5. `POST /auth/login/resend`

```json
{
  "attemptId": "<идентификатор попытки>"
}
```

Порядок:

1. Определить пользователя, заблокировать пользователя и попытку, перечитать состояние.
2. Отсутствующая, заменённая, подтверждённая или погашенная с `user_inactive` попытка даёт `400`. Погашенная с `attempts_exhausted` даёт `429`; восстановление только через новый login.
3. Просроченная непогашенная попытка допускает resend. Неактивный пользователь не допускает отправку.
4. Если с `last_sent_at` прошло меньше 60 секунд, вернуть `429` и оставшееся время.
5. В одной транзакции заменить `secret_hash`, установить новый `last_sent_at`, обнулить `attempts`. `attemptId` и сохранённый метод не меняются.
6. Зафиксировать изменение, затем отправить письмо. Старый секрет больше не действует.

**Решение для проекта:** если у ещё непогашенной попытки пользователь стал неактивен, погасить её с `user_inactive` и вернуть `401 invalid_credentials`, как при confirm. Повторное обращение к погашенной попытке даёт `400`. Это уточняет не полностью определённый источником ответ resend и не разрешает отправку неактивному пользователю.

Успех — `202`:

```json
{
  "method": "otp",
  "attemptId": "<тот же идентификатор попытки>",
  "expiresInSeconds": 600,
  "resendAfterSeconds": 60
}
```

При SMTP-ошибке — `503`; новый хеш остаётся в БД, старый не восстанавливается. Следующая отправка возможна через 60 секунд от обновлённого `last_sent_at`. При неудачном commit письмо не отправляется.

### 7.6. `POST /auth/refresh`

Тело не требуется. Источник токена — только cookie `refresh_token`; тело, query и Authorization не служат альтернативой.

1. Проверить Origin/CSRF и IP rate limit.
2. Проверить JWT: формат, только HS256, подпись refresh-ключом, issuer, audience, `iat`, `exp`, непустой корректный `sub`, `token_use=refresh`.
3. Найти пользователя по `sub`. Только `active` допускает продолжение.
4. Создать оба новых JWT от текущего серверного времени: access на 15 минут, refresh на 30 дней.
5. Установить обе cookies одним ответом `204` без тела.

Отсутствующая/неверная/просроченная cookie, неверный тип токена, неизвестный/неактивный пользователь — `401 invalid_session` без `Set-Cookie`. Недоступная БД или ошибка подписи — `503` без `Set-Cookie`, а не `401`. Старая cookie не удаляется и может использоваться повторно до её собственного истечения.

Новый refresh не отменяет старый. Его копии продолжают криптографически действовать до собственного `exp`; повторное использование не выявляется. Отдельный refresh нельзя отозвать адресно.

### 7.7. `POST /auth/logout`

- Тело отсутствует.
- Действительные JWT не требуются. Некорректные или отсутствующие cookies не препятствуют выходу.
- Для запроса, прошедшего Origin/CSRF-проверку, всегда вернуть `204` и удалить обе cookies с исходными именами, Path, Secure, SameSite и без Domain.
- Использовать истёкший срок и `Max-Age=0`; тело и сведения о пользователе отсутствуют.
- Logout не обращается к refresh-сессиям и не отзывает скопированные JWT на другом устройстве.
- При неверном Origin/CSRF действует общее правило `403 csrf_rejected`: «всегда 204» не отменяет защиту cross-origin POST.

Клиент после успеха очищает UI-состояние и показывает форму входа. API не реализует frontend.

### 7.8. Общая проверка access

Перед каждой защищённой операцией:

1. Прочитать только cookie `access_token`.
2. Проверить HS256, подпись access-ключом, issuer, audience, `iat`, `exp`, непустой корректный `sub`, `token_use=access`.
3. Найти пользователя, выбирая только `id` и `status`.
4. Пропустить только существующего `active` пользователя.
5. Передать дальше только проверенный `userId`, без ролей из claims.

Любой отказ токена или статуса — `401 invalid_session`. Недоступная БД — `503`. Успех продолжает pipeline, отдельного ответа нет.

Не требовать access для login/confirm/resend/refresh/logout, OpenAPI и health. Обязательный будущий вызов проверки оформляется общим механизмом, а не копируется по контроллерам. Для интеграционного теста достаточно защищённого endpoint, добавленного только в тестовый host; новый production endpoint профиля не требуется.

## 8. JWT и cookies

### 8.1. Claims

| Claim | Access | Refresh |
| --- | --- | --- |
| `sub` | ID пользователя | Тот же ID |
| `iss` | `JWT_ISSUER` | `JWT_ISSUER` |
| `aud` | `JWT_AUDIENCE` | `JWT_AUDIENCE` |
| `iat` | Серверное время выпуска | Серверное время выпуска |
| `exp` | `iat + 900 секунд` | `iat + 2592000 секунд` |
| `token_use` | `access` | `refresh` |

- Только HS256; access и refresh используют разные ключи.
- Не добавлять `jti`, роли, email, пароль/хеш, персональные данные.
- Проверять обязательное присутствие и корректный тип claims, а не только подпись. Для проекта `sub` должен разбираться как существующий тип ID пользователя.
- Допустимое рассогласование часов при проверке — не больше 30 секунд. Нельзя молча оставить большее библиотечное значение.
- **Решение для проекта:** проверять, что `iat` не находится в будущем сверх допустимого рассогласования и `exp > iat`. Время выпуска берётся только с сервера.
- Оба токена готовятся до любых `Set-Cookie`; проверка refresh access-ключом или наоборот запрещена.
- При stateless-контракте без `jti` две выдачи в одну секунду могут создать одинаковую строку JWT. Критерии проверяют claims и сроки, а не обязательное отличие строк.

### 8.2. Cookies

| Cookie | Атрибуты по умолчанию |
| --- | --- |
| `access_token` | `HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=900`, без `Domain` |
| `refresh_token` | `HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh; Max-Age=2592000`, без `Domain` |

Срок cookie согласован с `exp` соответствующего токена; задержка между подписью и ответом не должна продлевать cookie за срок JWT. Для другого site обе cookies используют `SameSite=None; Secure`.

Refresh-cookie с таким Path обычно не отправляется браузером на `/auth/logout`. Это не мешает удалить её ответом logout, если атрибут Path совпадает с исходным.

Токены не возвращаются в теле, URL или дополнительных доступных JavaScript заголовках. `Set-Cookie` используется только для предусмотренной установки cookies. Ошибки login/confirm/refresh не должны частично устанавливать, перезаписывать или удалять cookies.

## 9. HTTPS, CORS и CSRF

### Same-origin по умолчанию

Frontend и API работают на одном origin, cookies имеют `SameSite=Strict`. Наличие произвольного Origin не должно автоматически разрешать CORS.

### Другой доверенный origin

- В конфигурации задаётся точный доверенный frontend origin: схема, host и port.
- CORS разрешает только этот origin, credentials и необходимый `X-CSRF-Protection`; wildcard недопустим.
- Каждый изменяющий состояние cross-origin POST проверяет точное совпадение `Origin` и `X-CSRF-Protection: 1`, включая same-site, но cross-origin запросы.
- Preflight разрешает нужные методы и заголовки, но сам не меняет состояние.
- Другой site дополнительно требует `SameSite=None; Secure` на обеих cookies.
- Недоверенный origin или неверный CSRF-заголовок дают `403` с `csrf_rejected` до изменений БД и отправки письма.

**Решение для проекта:** запрос без `Origin` допускается для небраузерных HTTPS-клиентов, например Postman. `Origin: null` не считается отсутствующим и отклоняется. Same-origin запрос определяется по публичному API origin; за proxy используются только доверенные forwarded headers. Кросс-origin запрос без корректного защитного заголовка не допускается даже при наличии верных пароля/JWT.

### Локальный запуск и proxy

Текущий HTTP-only Docker не достаточен для браузерной проверки контракта. В будущем плане предусмотреть рабочую HTTPS-точку входа и инструкции: например, TLS termination перед API или HTTPS listener с локальным сертификатом. Выбор минимального способа остаётся составителю плана. Снимать `Secure` нельзя.

Если TLS завершается на proxy, внешний трафик остаётся HTTPS, а forwarded scheme и client IP принимаются только от настроенных доверенных proxy/network. Редирект сам по себе не заменяет TLS listener и не делает передачу пароля по HTTP безопасной. Документация клиента должна указывать сразу HTTPS URL.

## 10. Ошибки и частичное состояние

| HTTP | Условия |
| --- | --- |
| `400` | Невалидный login/confirm/resend; неверный либо просроченный секрет; отсутствующая, заменённая, использованная или ранее погашенная с `user_inactive` попытка |
| `401 invalid_credentials` | Неизвестный email, неверный пароль, неактивный пользователь; первое обнаружение неактивного пользователя в действующей попытке |
| `401 invalid_session` | Отказ access/refresh по любой проверке JWT либо пользователя |
| `403 csrf_rejected` | Недоверенный Origin либо провал CSRF; это не решение RBAC |
| `429` | Rate limit, отправка ранее 60 секунд, уже исчерпанные пять неверных OTP |
| `503` | БД, SMTP, подпись JWT или commit недоступны |

Пятый неверный OTP — намеренное исключение: сам пятый ответ `400`, последующий `429`.

| Момент отказа | Состояние | Повтор |
| --- | --- | --- |
| Login challenge до commit | Нет новой зафиксированной попытки, письма нет | Повторить login |
| Login SMTP после commit | Новая попытка существует | Resend или login после общей паузы |
| Resend до commit | Старый секрет остаётся | Повторить resend с учётом прежнего времени |
| Resend SMTP после commit | Новый хеш сохранён, старый недействителен | Resend после новой паузы |
| Confirm: подпись/commit | Успех не зафиксирован, cookies нет | Повторить confirm |
| Confirm: ответ потерян после commit | Challenge погашен | Новый login |
| Прямой login/refresh: подпись | Ни одна cookie не отправлена | Повторить; refresh действует до своего срока |

Доставка в SMTP и DB commit не являются общей транзакцией. Outbox и очередь доставки не добавляются: источник явно задаёт поведение `503` после сохранения challenge. Ошибка логирования не должна раскрывать секреты; детали инфраструктурных исключений не попадают клиенту.

## 11. Rate limiting

Обязательные пределы:

- Login: максимум 30 запросов на IP за минуту.
- Login: максимум 5 неуспешных проверок на сочетание нормализованного email и IP за 15 минут.
- Refresh: максимум 30 запросов на IP за минуту.
- OTP: максимум 5 неверных проверок одного challenge, атомарно в БД.
- Login/resend: отправка для непогашенной попытки не чаще раза в 60 секунд, под блокировками БД.

**Решения для проекта:**

- После пяти неудач шестая проверка пары email/IP отклоняется до bcrypt до освобождения окна. Успех не обнуляет ещё действующие неудачи.
- Неудача — нейтральный отказ `invalid_credentials`, включая неизвестный email и неактивный статус. Невалидный JSON и инфраструктурный `503` не расходуют этот счётчик.
- Ключ счётчика не хранит открытый email; использовать служебный HMAC-идентификатор.
- Параллельные запросы не должны проходить лимит за счёт гонки. Для пары email/IP проверки нужно координировать до bcrypt, сохраняя учёт именно неудач.
- Учёт времени не должен позволять удвоить предел коротким всплеском на границе fixed window; точное скользящее окно или эквивалентная строгая реализация остаётся составителю плана.
- Для текущего однорепличного учебного развёртывания допустим локальный limiter с ограниченным временем жизни записей. Перезапуск обнуляет его; для нескольких реплик потребуется общее хранилище/edge limiter. Redis и распределённый сервис сейчас не добавляются.
- Достоверность client IP обеспечивается настройкой доверенных proxy; произвольный `X-Forwarded-For` не должен обходить лимиты.

## 12. Аудит и журналы

События:

- Успехи и отказы login; срабатывания IP и email/IP лимитов.
- Создание/замена login challenge, resend, успех confirm, неверные секреты, истечение TTL, исчерпание OTP.
- Успехи и отказы refresh, logout, отказы access.
- Сбои БД, commit, SMTP и подписи.
- Отказы Origin/CSRF.

Поля: `userId`, если пользователь известен, вид события, метод, `attemptId`, результат, серверное время, request ID. Для неизвестного email — необратимый HMAC-идентификатор с отдельным audit key; не обычный некриптографический хеш email.

Причины JWT-отказов в журнале: `missing`, `malformed`, `signature`, `expired`, `claims`, `token_use`, `user_inactive`. Клиент всегда получает общий `invalid_session`.

Не журналировать открытый email, пароль, хеш пароля, OTP, magic-link token, HMAC/secret hash, JWT, `Cookie`, `Set-Cookie`, ключи, полный URL, полные тела или заголовки запросов. Исключить утечку через exception logging и HTTP logging middleware. Служебный HMAC-идентификатор email — разрешённое отдельное поле аудита; HMAC challenge в журнал не допускается.

Текущий `RegistrationAudit` необходимо перевести с открытого email на безопасный идентификатор или `userId` и обновить соответствующие тесты, не меняя HTTP-контракт регистрации. Существующие логи не очищаются этой работой.

## 13. OpenAPI, health и эксплуатация

- Описать все пять endpoints, обе формы confirm, поля ответов и обязательные ошибки, включая `503` с продолжением challenge.
- Документировать cookie-based access и refresh, атрибуты cookies, отсутствие JWT в JSON, Origin/CSRF и заголовок повтора.
- Не включать реальные JWT, OTP или ключи в примеры и сохранённые Postman environments.
- Существующий `GET /health` сохранить как liveness с прежним успешным контрактом.
- **Решение для проекта:** добавить `GET /health/ready`: доступная БД и успешно прошедшая startup validation дают `200`, недоступная БД — `503`. При неверном обязательном секрете host не запускается и readiness недоступна. SMTP не включать в частый readiness probe: фактический отказ отправки обрабатывается операцией.
- Существующие тесты и локальные инструкции запуска должны получить валидную auth-конфигурацию; для рабочего запуска не оставлять встроенных секретов.
- В плане перечислить изменения HTTPS, environment, compose/launch settings и README без перезаписи несвязанных пользовательских изменений.

## 14. Интеграционные ограничения и совместимость

1. Сохранить два проекта, существующий `AppDbContext`, migration history и `public partial Program`.
2. Существующий пользователь с bcrypt-хешем может войти без перерегистрации, если его статус `active`.
3. Регистрация по-прежнему не выдаёт сессию. Её повторный register возвращает текущий `409`.
4. Подтверждение регистрации и подтверждение входа используют разные таблицы и ключи. Старый registration challenge не является login challenge.
5. Особенность пятого OTP в login не должна незаметно изменить уже существующее поведение registration confirm.
6. Расширение почтового интерфейса требует обновить production sender, `NullEmailSender`, тестовые double и все вызовы, которых коснётся сигнатура.
7. Статусы добавляются без потери существующих пользователей. Изменять пароли/хеши или очищать таблицы при миграции запрещено.
8. Access/refresh и ошибки БД не должны перехватываться текущим registration exception mapping с неверным кодом.
9. Изменения аудита обновляют тесты, ожидающие email, но не ослабляют запрет на чувствительные данные.
10. Миграции проверяются на реальном PostgreSQL; in-memory provider не доказывает блокировки и частичный уникальный индекс.

## 15. Критерии приёмки и проверки

### Login и существующая регистрация

- Active + правильный пароль, подтверждение выключено: `204`, ровно обе cookies, без тела.
- Нормализация email работает; пароль, включая пробелы, проверяется без изменения.
- Неизвестный email, неверный пароль, каждый неактивный статус имеют одинаковые `401` и `invalid_credentials`.
- Для неизвестного email действительно выполняется dummy bcrypt verify; валидация/лимиты предшествуют дорогой проверке.
- Невалидный email, отсутствующий/пустой пароль, превышение bcrypt byte limit дают `400`.
- Ранее зарегистрированный active пользователь входит; pending не активируется через login.
- Все прежние тесты регистрации, resend, health и миграций сохраняют ожидаемое HTTP-поведение.

### Challenge: оба метода

- `202` содержит только разрешённые поля; письмо содержит секрет, JSON и логи — нет.
- JWT/cookies не выдаются до успешного confirm.
- OTP с ведущим нулём работает; неверные/смешанные формы отвергаются без расхода счётчика.
- Правильный пятый OTP успешен; пятый неверный даёт `400`, следующий — `429`.
- Magic link имеет 32 случайных байта секрета; секрет находится во фрагменте URL, неверный token не расходует OTP-счётчик.
- Повторное подтверждение, заменённая попытка, неверный секрет, TTL ровно 600 секунд и более дают предписанный отказ.
- GET ссылки не подтверждает вход. POST с правильным token подтверждает его один раз.
- Смена настройки метода или выключение подтверждения не ломает существующие confirm/resend.
- Resend до 60 секунд даёт `429` и оставшееся время; ровно через 60 секунд разрешён.
- Resend просроченной непогашенной попытки работает; исчерпанная требует нового login.
- Resend сохраняет method/attemptId, сбрасывает attempts и TTL, старый секрет не принимается.
- Неактивный или удалённый пользователь не получает новую пару JWT и письмо.

### Конкурентность и сбои

- Параллельные login не создают две непогашенные попытки.
- Login/resend делят паузу, включая SMTP failure; гонка не отправляет два письма в одной паузе.
- Параллельные OTP не превышают пять неверных проверок, успешный challenge используется один раз.
- Confirm/resend и изменение статуса не обходят актуальную проверку пользователя.
- DB rollback не приводит к отправке письма или cookies.
- SMTP failure после commit сохраняет новый хеш и паузу; login `503` содержит данные для продолжения без секрета.
- Искусственный отказ второй подписи и отказ commit подтверждения дают `503` без любой `Set-Cookie`; повтор после rollback возможен.

### JWT, refresh и access

- Проверяются алгоритм, подпись, issuer, audience, `iat`, `exp`, `sub`, `token_use`; отсутствующие и неверно типизированные claims отвергаются.
- Access нельзя использовать как refresh, refresh — как access; чужой ключ и любой алгоритм кроме HS256 отвергаются.
- Проверены границы времени и clock skew не более 30 секунд.
- Refresh берётся только из cookie; передача JWT через body/query/Authorization не заменяет её.
- Refresh даёт новую пару с TTL от текущего времени и без server-side session.
- Старая refresh-копия после обновления и logout продолжает работать до своего срока только для active пользователя.
- Для каждого статуса, отсутствующего пользователя и недоступной БД проверены отдельно login, confirm, refresh и access.
- БД недоступна: `503`, а не `401`; ошибки refresh не удаляют прежнюю cookie.
- RBAC-потребителю передаётся только проверенный `userId`; роли из JWT не принимаются.

### Cookies, logout, CSRF и лимиты

- Проверены имена, HttpOnly, Secure, SameSite, Path, отсутствие Domain и согласованность срока с JWT.
- Logout идемпотентен с отсутствующими, валидными и повреждёнными cookies, удаляет обе с правильными Path.
- Same-origin, доверенный cross-origin same-site и cross-site сценарии проверены отдельно.
- Недоверенный/`null` Origin и отсутствующий/неверный защитный заголовок cross-origin запроса дают `403 csrf_rejected` без побочных действий.
- Разрешённый preflight корректен; CORS не использует wildcard с credentials.
- Проверены 31-й login/refresh на IP, шестая проверка после пяти отказов email/IP, границы окон и параллельные запросы.
- Недоверенный forwarded header не меняет надёжно определённые client IP и публичный origin.

### Журналы, конфигурация и запуск

- Все обязательные события и безопасные поля присутствуют; причины JWT-отказа категоризированы.
- Перехваченные логи не содержат запрещённых данных, включая registration path, request URL и SMTP/JWT exceptions.
- Отсутствующие, короткие, невалидные и повторно использованные ключи, пустые issuer/audience останавливают запуск.
- Liveness совместима с текущим контрактом; readiness различает доступность БД.
- HTTPS-сценарий проверяется отдельно в реальном локальном браузере/клиенте: HTTPS base address in-memory теста не доказывает TLS контейнера.
- OpenAPI соответствует фактическим ответам, включая отсутствие тела у `204` и обе формы confirm.
- Покрытие тестами не ниже 80%; **решение для проекта:** проверять line coverage production-проектов, исключив generated-код и EF migration snapshots, но не auth-логику.
